# Дизайн-заметка

## Что строим
Среда для агентов-аудиторов: компания с книгами (проводки, счета, платежи, курсы, документы), в которую
генератор внёс ошибки четырёх типов. Агент читает книги инструментами, сдаёт один submit с выводами,
судья сопоставляет выводы с эталоном и выдаёт награду `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`.

## Главные решения и почему

| Решение | Почему |
|---|---|
| Хост владеет средой и судьёй, агент в отдельном процессе (JSON-строки по stdin/stdout, песочница audit-hook) | Простое скрытие полей в объекте не изоляция. Агент не импортирует оценщика и не видит каталог эпизода. Настоящая граница: контейнер с `--network none` |
| Среда читает только белый список открытых файлов (`env/loader.py`) | truth/provenance не могут попасть в наблюдения даже по ошибке; в закрытом режиме truth не открывается вообще (тест шпионит за `open`) |
| Генератор детерминирован: только `random.Random(seed)`, байты файлов одинаковы по seed и не зависят от PYTHONHASHSEED | Повторяемость и проверка «пересоздай по provenance» |
| Ошибки вносятся в согласованные книги, а эталон получается из изменения | Независимый валидатор (`qa/evidence.py`) выводит каждую ошибку из открытых данных по правилам policy.json, не глядя в код генератора |
| Судья: точное сравнение, максимальное паросочетание, детерминированный выбор при равенстве | Порядок выводов не влияет на результат; повтор вывода остаётся ложным (определения жюри) |
| Каждый шаг тратит бюджет, включая ошибочные; submit в лимите 100, но не в inspection_steps | Нельзя перебирать ID бесплатно; награда за экономию шагов честна |
| В ответе политике в закрытом режиме reward = 0, истинная награда считается отдельно (`score_episode`) | Политика не может подгонять поведение под скрытую награду |

## Поток данных

```
generate_episode ──► episode_dir (открытые файлы + truth/provenance, видит только жюри)
                        │
        reset(closed) ──┤ читает ТОЛЬКО manifest, ledger, invoices, payments, fx, policy, docs
                        ▼
   политика (отдельный процесс) ⇄ step({"name","args"}) ⇄ judge_adapter ⇄ AuditEnv
                        │ submit
                        ▼
        score_episode(episode_dir, findings, inspection_steps) ─► tp/fp/fn/P/R/F1/return
```

## Четыре типа ошибок и их канонический вид

| type | affected_ids | claimed_amount_minor | доказательства (один из наборов) |
|---|---|---|---|
| `duplicate_invoice` | оба счёта (оригинал и копия) | сумма счёта | документы обоих счетов |
| `missing_or_partial_allocation` | счёт и платёж | недоприменённая сумма в валюте счёта | документ платежа + строка проводки по платежу (`R…`) |
| `wrong_date_or_fx_rate` | счёт и платёж | разница зачёта в валюте счёта | документ платежа + запись курса `FX:…` (или запись курса + две проводки платежа) |
| `period_cutoff` | счёт | сумма счёта | документ счёта + строка проводки счёта (`R…`) |

## Сложность и сценарии
Профили `clean / easy / medium / hard` = 0 / 2 / 6 / 12 ошибок; каждый тип включается отдельно через
`config["errors"]`. Два сценария взаимодействия: `partial_cross_currency_boundary` (кросс-валютный
частичный платёж у границы периода: ошибка курса + частичное распределение) и `duplicate_with_fx_error`
(дубль счёта, у которого ещё и неверный курс). Законные «отвлекающие» случаи: подписки, возврат → повторный
счёт, счета и платежи на границе периода, JPY без копеек.

## Лестница сложности
oracle 1.00 > careful 0.97 > careful_dup 0.20 > reconcile −0.54 > random −0.99 ≥ flag_all −1.00.
Она показывает, что среда различает аккуратную работу, частичное решение и шум.

## Проверки качества
`make audit` самооценивает проект по пяти критериям жюри (контракт и изоляция, данные и эталон, награда,
воспроизводимость, инженерия), включая прогон определений жюри C01–C20, D01–D20, matcher 1–20 + M01–M12 и
пар P01–P20. Это наша самооценка, не оценка жюри.
